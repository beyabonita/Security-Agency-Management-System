3.14 Use Case Scenario

Table 3: Login
Use Case 1: Login
Use Case Goal: To verify user identity, enforce registered device checking, and grant access to role-specific system features.
Scenario 1: Successful Login
Actor: Guard, Operations Head, Inspector, Super Admin
Pre-condition: User has an active account. Security Guard must use their registered device.
Main Flow:
Step 1: User enters Email and Password.
Step 2: System triggers <<include>> Authenticate User.
Step 3: System verifies credentials against the database and checks registered device ID for Guard.
Step 4: System determines user role and redirects to the appropriate dashboard.
User Action: Inputs credentials and clicks "Login."
System Response: Grants access, validates device binding, and loads the role-specific interface.
Table 4: Manage Accounts
Use Case 2: Manage Accounts
Use Case Goal: To provision administrative accounts, update user information, and manage platform permissions.
Scenario 1: Account Management & Provisioning
Actor: Super Admin
Pre-condition: Super Admin is logged in with administrative access.
Main Flow:
Step 1: Super Admin navigates to the "User Management / Account Access" section.
Step 2: System triggers <<include>> Add Account when Super Admin clicks "Add New User."
Step 3: Super Admin selects the specific role (Operations Head or Super Admin).
Step 4: Super Admin enters personal details: Name, Email, Mobile Number, and Password.
Step 5: Super Admin clicks "Register / Create Account."
Step 6: Super Admin updates details or permissions and clicks "Save Changes."
User Action: Fills out the form, modifies permissions, and submits.
System Response: Validates data, updates user database, and returns confirmation.
Table 5: Execute System Check
Use Case 3: Execute System Check
Use Case Goal: To test platform integrity, database response times, and system diagnostic health.
Scenario 1: Comprehensive Diagnostic Routine
Actor: Super Admin
Pre-condition: Super Admin is logged in with administrative oversight privileges.
Main Flow:
Step 1: Super Admin opens the "System Controls" dashboard and selects "System Diagnostics."
Step 2: Super Admin clicks "Execute System Check."
Step 3: System tests database connectivity, active services, and cloud storage health.
Step 4: System displays diagnostic summary with ping latency and operational status indicators.
User Action: Clicks "Execute System Check" to initiate diagnostics.
System Response: Performs automated checks across system layers and renders live operational status.
Table 6: Manage Personnel
Use Case 4: Manage Personnel
Use Case Goal: To maintain security guard and inspector personnel records, employment contracts, and license uploads.
Scenario 1: Add and Manage Personnel
Actor: Operations Head
Pre-condition: Operations Head is logged in and navigates to Personnel module.
Main Flow:
Step 1: Operations Head opens "Personnel" and clicks "Add Personnel."
Step 2: System triggers <<include>> Add Personnel and auto-generates Personnel ID.
Step 3: Operations Head selects role (Guard or Inspector) and duty type (Regular or Contract).
Step 4: Operations Head enters personal details: Name, Email, Mobile Number, and Contract Dates.
Step 5: Operations Head uploads license documents and clicks "Save Personnel."
Step 6: System triggers <<extended>> Archive Personnel when an inactive personnel profile is selected for removal.
User Action: Enters personnel details, updates profiles, or archives personnel.
System Response: Validates duplicate numbers, saves profile to the database, and updates active roster.
Table 7: Manage Sites
Use Case 5: Manage Sites
Use Case Goal: To define client deployment locations and geographical geofence boundaries for security posts.
Scenario 1: New Deployment Site and Geofence Setup
Actor: Operations Head
Pre-condition: Post location is known.
Main Flow:
Step 1: Operations Head navigates to "Deployment Sites" and clicks "Add Company."
Step 2: System triggers <<include>> Add Locations to record site name and address.
Step 3: Operations Head inputs GPS coordinates or selects the location on the interactive map.
Step 4: System triggers <<extended>> Set Radius to configure the geofence perimeter (e.g., 100 meters).
Step 5: Operations Head clicks "Save Deployment Site."
User Action: Sets coordinates and radius then saves.
System Response: Maps the virtual geofence boundary and links it to the specific client site.
Table 8: Manage Duty Schedules
Use Case 6: Manage Duty Schedules
Use Case Goal: To designate guards to specific posts, build weekly duty schedules, and assign rest days.
Scenario 1: Successful Assignment & Schedule Modification
Actor: Operations Head, Inspector
Pre-condition: Guard and Deployment Site exist in the system.
Main Flow:
Step 1: User opens the "Duty Scheduling" module and selects the Client site.
Step 2: System triggers <<include>> Choose Date and Time to set 7-day schedule and shift hours.
Step 3: System triggers <<include>> Assign Guard to select a stationed Guard for each shift slot.
Step 4: User designates weekly rest days and checks for scheduling conflicts.
Step 5: User clicks "Assign Schedule."
Step 6: System triggers <<extended>> Change Schedule when an existing schedule requires modification.
User Action: Selects parameters, assigns guards, and confirms roster.
System Response: Updates schedule database, checks for conflicts, and notifies assigned Security guards.
Table 9: Process Duty Requests
Use Case 7: Process Duty Requests
Use Case Goal: To review and process guard absence, shift swap, and overtime requests.
Scenario 1: Request Submission and Approval
Actor: Guard (submits), Operations Head (reviews & approves)
Pre-condition: Guard has an assigned shift and submits a formal request via the mobile app.
Main Flow:
Step 1: Guard opens "Duty Requests" in mobile app, selects request type (Absence, Swap, or Overtime), and attaches optional letter.
Step 2: Operations Head navigates to the "Duty Requests" module on the web portal.
Step 3: Operations Head examines request details, replacement guard availability, and attached letter.
Step 4: Operations Head clicks "Approve."
Step 5: System triggers <<include>> Approve Request.
Step 6: System automatically updates the roster (swapping assignments or excusing absence) and notifies the guards.
User Action: Guard files request; Operations Head reviews details and clicks approve.
System Response: Updates schedule database in real time and sends automated notifications to the guards.
Table 10: Attendance Punch
Use Case 8: Attendance Punch
Use Case Goal: To record the official time-in and time-out of security personnel with geofence and live face verification.
Scenario 1: Successful Time-In within Geofence with Live Face Capture
Actor: Guard
Pre-condition: Guard is at the assigned post, shift is active, and device is verified.
Main Flow:
Step 1: Guard opens the mobile app and clicks the "Time-In" (or "Time-Out") button.
Step 2: System compares device GPS coordinates with the stored Geofence radius.
Step 3: System triggers <<include>> Capture Face Photo using the in-app camera.
Step 4: Guard takes a live selfie photo; system stamps geotag watermark overlay.
Step 5: System records the exact server time, GPS coordinates, and photo evidence.
Step 6: System triggers <<extended>> Force Attendance if guard is outside geofence during emergency.
User Action: Clicks "Time-In," allows GPS access, and takes live selfie photo.
System Response: Displays "Time-In Successful," records attendance log, and updates live tracker.
Table 11: Report Incident
Use Case 9: Report Incident
Use Case Goal: To provide a detailed account of security issues encountered on site with attached photo or video evidence.
Scenario 1: Standard Incident Reporting
Actor: Guard
Pre-condition: Guard is logged in and on an active clocked-in shift.
Main Flow:
Step 1: Guard selects "Create Incident Report" from the mobile menu.
Step 2: Guard selects Incident Category (e.g., Theft, Trespassing, Fire, Medical, Damage).
Step 3: Guard enters title and types a detailed narrative description of the event.
Step 4: System triggers <<include>> Attach Photo/Video.
Step 5: Guard uses the camera to capture photo or video evidence.
Step 6: Guard reviews the summary and clicks "Submit."
User Action: Fills out the form, takes photo/video, and confirms submission.
System Response: Uploads data to Incident Database, sets status to "Under investigation," and alerts supervisors.
Table 12: Manage Report Incident
Use Case 10: Manage Report Incident
Use Case Goal: To allow supervisors to validate, evaluate, and update the resolution status of incident reports.
Scenario 1: Evaluating, Reviewing, and Resolving Incident Report
Actor: Operations Head, Inspector
Pre-condition: Incident reports are submitted and pending review in the system.
Main Flow:
Step 1: Inspector or Operations Head navigates to the "Incidents" section on the web console.
Step 2: User clicks on a specific report to open full details and examine photo/video evidence.
Step 3: User examines the timestamp, description, GPS location, and evidence media.
Step 4: User enters findings in the "Reviewer Note" field.
Step 5: User updates status (Under investigation, Escalated, or Resolved) and clicks "Save Review."
Step 6: System triggers <<extended>> Archive Incident when moving resolved records to archives.
User Action: Opens report, reviews data and evidence, enters notes, and updates status.
System Response: Saves reviewer note, updates incident status in the database, and syncs across consoles.
Table 13: View Incident
Use Case 11: View Incident
Use Case Goal: To examine historical incident records, risk areas, and view attached photographic evidence.
Scenario 1: Incident History & Area Risk Inspection
Actor: Inspector, Operations Head
Pre-condition: Incident logs exist in the system.
Main Flow:
Step 1: User opens the "View Incidents / Incident Logs" feed on the web portal.
Step 2: User applies filters by date range, post location, category, or status.
Step 3: System displays matching incident summary entries and area risk indicators.
Step 4: User clicks an entry to view full incident details, location map, and photo/video evidence.
User Action: Applies filters and selects incident records for inspection.
System Response: Displays full incident details, location coordinates, and photo/video evidence.
Table 14: View DTR
Use Case 12: View DTR
Use Case Goal: To inspect Daily Time Records, rendered work hours, tardiness, and undertime logs.
Scenario 1: Checking Daily Time Records & Punctuality
Actor: Guard, Operations Head, Inspector
Pre-condition: Attendance records exist in the database.
Main Flow:
Step 1: Guard opens "Duty Logs / DTR" in mobile app, or Supervisor opens "DTR Monitoring" on web portal.
Step 2: User selects the Month and Cut-off period (1st–15th or 16th–end of month).
Step 3: System compares actual punch times against scheduled shift hours.
Step 4: System displays attendance table with dates, actual punch times, tardiness, undertime, overtime, and total hours.
User Action: Selects pay period and reviews attendance logs.
System Response: Calculates cumulative hours, applies tardiness/undertime formulas, and displays detailed DTR table.
Table 15: Export DTRs
Use Case 13: Export DTRs
Use Case Goal: To produce formal PDF documents of guard Daily Time Records for payroll and auditing.
Scenario 1: Exporting DTR to PDF
Actor: Operations Head
Pre-condition: Attendance logs exist in the system for the selected cutoff period.
Main Flow:
Step 1: Operations Head navigates to the "Export DTRs / Attendance Reports" section.
Step 2: Operations Head selects cutoff period and client post or guard filter.
Step 3: System triggers <<include>> Generate PDF to compile 6-column DTR summary with certified signature lines.
Step 4: Operations Head clicks "Download / Export DTR."
User Action: Selects filters and clicks export.
System Response: Generates and downloads a formatted, print-ready PDF file for the user.
